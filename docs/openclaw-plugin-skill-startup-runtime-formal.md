# OpenClaw Plugin / Skill：启动时 vs 运行时（正式说明）

## 1. 结论
- **Plugin** 用于把能力接入 OpenClaw 并提供可执行的系统级扩展：启动时加载并注册能力入口，运行时承接调用并执行。
- **Skill** 用于固化方法与流程（SOP）：通过提示词注入影响模型如何选择工具、如何填写参数、如何处理失败与输出格式。

换句话说：**Plugin 扩展“系统能力与执行”，Skill 扩展“使用方法与流程”。**

---

## 2. 启动时（Startup）：Plugin 的职责
启动时关注“系统是否具备该能力”以及“能力是否可配置、可治理”。

Plugin 在启动/加载阶段通常完成：
1) **加载**：被 Gateway 发现并加载。
2) **初始化运行环境**：准备鉴权、HTTP 客户端/连接池、重试/超时/限流策略、日志与观测，必要时建立数据库/队列连接。
3) **注册能力入口**：将扩展能力注册到 OpenClaw（例如注册 tools、命令、handlers 或模型 provider/auth 流程）。

启动时的关键产物是：OpenClaw 在系统层面“认识并持有”这项能力入口。

---

## 3. 运行时（Runtime）：Plugin 与 Skill 的分工
运行时关注“一次具体请求如何完成”。

- **Skill（运行时前置）**：提供策略与步骤，指导模型做出正确的工具选择与参数构造，并定义失败兜底与输出格式。
- **Plugin（运行时执行）**：当模型发起调用（例如 tool call 或系统内部的 provider 调用）后，Plugin 执行真实的 I/O 与业务逻辑，并返回结构化结果。

因此：
- Skill 决定“怎么做更对、更稳、更符合规范”；
- Plugin 决定“这次调用能否被可靠执行、是否可观测、是否可审计”。

---

## 4. 示例：内部模型接入 OpenClaw（Provider 方式）
目标：使内部模型成为 OpenClaw 的系统级能力（可统一鉴权、可配置、可运维）。

### 4.1 启动时
- Plugin 被加载。
- 初始化内部模型调用底座：鉴权与凭证、HTTP client、路由/多租户策略、超时/重试/限流、日志与审计字段。
- **注册内部模型的 provider/auth 能力**：使 OpenClaw 在系统层面识别该内部模型，并将其纳入配置与治理。

### 4.2 运行时
- 每次推理请求走该 provider 路径，由 Plugin（provider 实现）执行。
- 统一处理可靠性与治理：token 获取/刷新、超时、重试、限流、错误分类、审计与观测，并在必要时降级。

---

## 5. 对比：仅使用 Skill 调用内部模型的边界
如果仅通过 Skill 在会话中调用内部模型，通常形态为：在某次对话中使用脚本/HTTP 调用完成一次请求。

该方式的边界是：
- 能实现“会话级调用”，但不等价于“系统级接入”；
- 难以在网关层统一治理（鉴权、限流、审计、观测与稳定性策略容易分散在脚本与提示词中）。

结论：**Skill 适合方法论与流程固化；内部模型接入若要系统化治理，应以 Plugin/provider 方式落地。**
